### 🚨 事故：`git stash` 摧毁 `.git`（2026-09-20 上午，已完整恢复）

**事故链**：为测基线执行 `git stash -q && go test && git stash pop -q`。该仓库根 `.git` 里挂着 **kilo worktree**（`.kilo/worktrees/pinto-marquis/.git` 是个 gitdir 指针文件，指向 `D:/code/xpilot/.git/worktrees/pinto-marquis`）。`stash` 运行时把**整个 `.git` 目录（含 objects/、refs/）卷进了回收站**，随后 `stash pop` 报 `not a git repository`。**这不是 git 的常规行为，是本仓库特殊结构下的炸法。**

**关键教训（硬规则）**：
1. **在 xpilot（及任何挂 worktree 的仓库）里，禁止用 `git stash` 测基线。** 要对比改动前后，改用：`git diff` 看改动 / 把文件复制到临时目录再 `git checkout` / 或直接 `git -c core.hooksPath= stash` 之外的一切手段。**`stash` 是禁招。**
2. 需要"干净基线"时，用 `git worktree add` 开临时工作树，或 `git archive HEAD | tar -x -C /tmp/baseline`，绝不碰主 `.git`。
3. 恢复窗口极窄：回收站条目是**按文件/目录粒度**存的，`.git` 被拆成 211 条（105 个 objects 分片 + refs + 各元数据）。**一旦回收站被清空或系统还原，就只剩重 clone。**

**恢复方法（已验证有效，可复用）**：
- 回收站 `$I*` 文件是 UTF-16LE 元数据：`[0:8]头 [8:16]大小 [16:24]mtime [24:28]名称长度(字符) [28:]名称(UTF-16LE，尾部带 \x00)`。**必须 `replace("\x00","").strip()`**，否则 Windows 路径报 `embedded null character`。
- 对应载荷是 `$R<同名>`。按路径深度升序重建（父目录先建）。
- 脚本思路见本次 `recover_git.py`（用完即删）。
- 恢复后补漏：`git rev-list --objects --all | while read sha p; do git cat-file -e $sha || echo MISSING $sha $p; done`。本次补回 1 个缺失 blob：`.gitignore`——**内容与工作区现有文件一致，`git hash-object -w .gitignore` 即可补回**。
- 损坏 reflog 直接 `rm -rf .git/logs`（重建成本为零，比逐个修快）。

## 修复「应用默认节点」点击卡顿 + BUG-3 数据竞争（已实现并验证）

用户反馈：「立即选点」即点即有反应，「应用默认节点」反而卡一下。

**根因（三条叠加，都在前端反馈链上，不是后端慢）**：
1. `handleRun` 走 `startSelection()`，**同步**置 `s.running=true` + `s.stage="准备中"` 并推 SSE `stage` → 前端立刻置灰。
   而 `handleDefaultNode` 把 `s.running=true` 放在 **goroutine 内部**，`writeJSON` 早已返回 →
   前端拉到快照仍是「空闲」→ 按钮不变灰 → 要等 goroutine 跑完推 `done` 才刷新，表现为「卡一下直接复原」。
2. 前端 `act()` 里有写死的 `setTimeout(refresh, 500)`：请求都返回了还硬等 500ms 才拉快照。
   立即选点因有 SSE 中间事件掩盖了这个延迟，应用默认节点没有中间事件，只能干等。
3. 置灰延迟 → 用户以为没点上 → 连点 → 两次请求都通过 `running` 检查 → **并发触发两次 `applyWinner`**。
   **这就是 BUG-3 的真实触发路径**。用户说的「限制点一下体验很差」根因在此：不是防重入不好，是反馈没做对。

**修复**：
- `service.go: handleDefaultNode` 重写，对齐 `startSelection` 时序：锁内一次读完 `running`/`cfg`/校验/置位（消除锁外读 `s.cfg`），
  锁外 `pushEvent("stage","应用默认节点中")`。**探针实测：返回后 `running=true`，耗时 0s。**
- `console.html`：新增 `setRunning(v, stage)`（乐观置灰 + 重绘按钮 + 更新阶段文字），
  SSE `stage` 分支改用它；`act()` 改为「点击即置灰 → 请求 → 失败才复原并 alert → 立刻 `refresh()`」，
  **删掉 `setTimeout(refresh, 500)`**；`running` 为真时本地直接 return。

**验证**：
- 临时探针 8 条全 PASS：两接口返回后 `running` 均为 true、stage 事件格式正确、空链接被拒且不置位、
  两接口重入被拒、**并发 10 次点击仅 1 次通过**（这条直接证明 BUG-3 已堵死）。
- `gofmt -l` 主目录为空、`go vet .` 零告警、`go build` OK。
- `go test .`：5 个通过，`TestRegistryPAC` 因沙箱拉黑 `reg.exe` 而失败（环境限制，非本次改动）。

## xpilot 的 pac 规则解析（15:07 用户提问：是不是只有列表内域名走代理）

### 结论：是的，白名单式的黑名单 —— 列表内走代理，其余**全部直连**

`C:\Users\wangchaojun\AppData\Roaming\xpilot\html\pac`，6835 行，逻辑只在最后 30 行：

```javascript
var proxy = 'PROXY 127.0.0.1:10808;DIRECT;';
var rules = [ [ [], [ …6788 个域名… ] ], [ [], [] ] ];

function FindProxyForURL(url, host) {
    for (var i = 0; i < rules.length; i++) {
        ret = testHost(host, i);
        if (ret != undefined) return ret;
    }
    return 'DIRECT';          // ← 全部没命中 → 兜底直连
}

function testHost(host, index) {
    for (var i = 0; i < rules[index].length; i++) {
        for (var j = 0; j < rules[index][i].length; j++) {
            lastRule = rules[index][i][j]
            if (host == lastRule || host.endsWith('.' + lastRule))
                return i % 2 == 0 ? 'DIRECT' : proxy;
        }
    }
    lastRule = '';
}
```

### 匹配语义
- `host == 规则` → 精确命中
- `host.endsWith('.' + 规则)` → 子域名命中父域规则。**带点**很关键：
  实测 `notgoogle.com` **不会**误命中 `google.com`（否则就是经典后缀陷阱）
- 兜底 `return 'DIRECT'` → 循环跑完没命中，直连

### 数组结构与「奇偶切换」的真相
```
rules[0] = [ [], [6788 个域名] ]   ← 域名全在这里
rules[1] = [ [], [] ]              ← 空的
```
这是标准 gfwlist→PAC 转换产物：`[ [], [域名…] ]` 形式，**`i % 2` 的 `i` 是
`testHost` 里那个内层循环变量**（第 2 层子块的索引），不是外层 `index`。
实测 `www.google.com` 命中 `{block:0, sub:1, j:2349}` → `sub=1` 为奇数 → **PROXY**。
所以「偶数子块=DIRECT、奇数子块=PROXY」的奇偶交替设计，靠 **空的 `rules[1]`**
把 `block` 这一维固定住，实际生效的一直是 `rules[0]` 内层的 `sub` 奇偶。

**注意坑**：`testHost` 里 `var i` **遮蔽**了 `FindProxyForURL` 的 `var i`。
两个函数各自独立作用域所以没出错，但读代码时极易把 `i % 2` 误认成块索引起作用 —— 我第一眼就读错了。

### 实测（直接 Node 载入 pac 的 JS 执行，非静态推断）
| 域名 | 决策 |
|---|---|
| chatgpt.com | PROXY |
| api.github.com | PROXY（子域命中 github.com） |
| taobao.com | DIRECT |
| qq.com | DIRECT |
| some-random-site.xyz | DIRECT（未列举 → 兜底） |
| notgoogle.com | DIRECT（未被 google.com 误伤） |

### 与其他层的关系（回到之前的结论）
- **PAC 优先于 xray 路由**：PAC 判 DIRECT 的流量根本不进 xray
- PAC 只管「域名 → 走不走 127.0.0.1:10808」
- xray 只管「进来了的 → 走 proxy 还是 direct」（geoip:private / geosite:cn / geoip:cn 三条规则）
- 两层口径不同但互补：PAC 是域名白名单制，xray 是国内直连制

**对用户的意义**：想给某个新网站走代理，直接在 pac 里加域名即可，
不用动 xpilot 配置、也不用重启 —— 但改完要点控制台的「刷新 PAC」让浏览器重新拉取。

## pac 重写为简洁版 + 等价性验证（15:11 用户质疑「为什么写这么复杂」）

必须保留 `host === rule || host.endsWith("." + rule)` 的后缀匹配，这段**没法简化**。

- 新增文件头注释：说明判定口径、匹配规则、**明确警告不要用 `includes`**
- 保留 `html/pac.src`（从 `git show HEAD:html/pac` 取回）作为转换脚本的输入
- 新增 `tools/pac_rewrite.js`（展开）与 `tools/pac_equiv.js`（等价性验证）

**33,798 个用例，真正的逻辑差异 0**。用例覆盖：每条域名本身 + `www.`/`a.b.` 子域 +

### ★ 最大的坑：验证脚本自己手抄逻辑，导致「自证」
写这个验证脚本时连续踩了三个同类错误，**每一个都会让验证结论变成假的**：

1. **手抄新版 `decide()` 时漏了 `toLowerCase()`** → 报「0 差异」，
   而我单独测 `GOOGLE.COM` 时明明是分叉的。手抄的那份和真文件行为不同。
2. **测试集大小写样本太少**（只有一条 `GOOGLE.COM`）→ 掩盖了分叉的方向。
   后来改成对**全部 6788 条域名**都造大写/首字母大写变体，才暴露出 13,385 条差异。
3. **调用签名写错**：PAC 规范是 `FindProxyForURL(url, host)` **两参**，

**修正后的原则（写进脚本注释了）**：
> 验证「文件 A 与文件 B 行为一致」时，**两边都必须执行真实文件**（用 `new Function` 整份 eval），
> 任何一方手抄都可能抄漏，让验证退化成自我确认。且必须按**真实签名**调用。

## 追加：`endsWith` polyfill 的去留确认（15:20）

### 起因
主人问「原版里我记得还有一个方法是修复 Firefox 的 bug 的，这里不需要吗？」
—— 指原版 `html/pac` 尾部那段：

```javascript
// REF: https://developer.mozilla.org/.../String/endsWith
if (!String.prototype.endsWith) {
    String.prototype.endsWith = function(searchString, position) { ... };
}
```

### 查证结论（★ 答案与主人记忆不同，已当场纠正）
- **真实身份**：这是 `endsWith` 的 **polyfill**，逐字照抄自 MDN 官方 Polyfill 段落
  （MDN 页明确写 "Polyfill of String.prototype.endsWith in core-js"）。
- **不是「修 Firefox 的 bug」**。它是 gfwlist 转 PAC 工具在 2015 年前后
  为兼容老浏览器塞进模板的通用兜底。主人大概是被注释里的 MDN 链接误导。
- 与 Firefox 相关的 PAC 注意事项是另一个东西：`network.proxy.autoconfig_url.include_path`
  （控制是否把 URL 路径传给 PAC），与 `endsWith` 无关。
- **Firefox PAC 环境的真实约束**：跑在受限 SpiderMonkey 沙箱，DOM / `window` /
  WebExtension API 全部不可用；SwitchyOmega 的 PAC Profile 在 Firefox 上
  因 AMO 政策直接不可用（另一条无关线索，供参考）。
- **`endsWith` 支持情况**：ES6（2015-09）进入基线，Firefox 17 起原生支持。
  如今在用的浏览器全部自带 → 原版那段是**纯空转的死代码**。
- **删掉反而更稳**：在受限沙箱里给内建 `String.prototype` 打补丁，
  若属性只读/引擎禁用会**抛异常并中断整个 PAC 文件** —— 风险大于收益。
- **★ 若未来真要兼容极老引擎，正确做法是「不依赖 `endsWith`」**
  （`host.slice(-(rule.length + 1)) === "." + rule`，纯 ES3），
  **而不是加回 polyfill**。主人决定不加，理由「现在没人用那么老的了」。

### 当前实际状态（重要）
- **polyfill 早在上一轮重写时就已删除**；本次未改任何代码 —— 指令在代码层面
  已达成。已用 grep 双向确认：`html/pac` 与 `%AppData%\xpilot\html\pac` **各 0 处**。
- 新版 `html/pac` 全 6814 行，非域名行仅：注释 + `var proxy` + `var proxyList = [`
  + `]` + `FindProxyForURL`(2 行) + `matchAny`(6 行) + 3 行注释。

### 实测：新版实际语法依赖（已剥离注释）
| 特性 | 是否使用 |
|---|---|
| `var` 声明 | ✓ |
| 普通 `for` 循环 | ✓ |
| `.endsWith()` | ✓ |
| `.toLowerCase()` | ✓ |
| `let`/`const` | ✗ |
| 箭头函数 `=>` | ✗ |
| 模板字符串 | ✗ |
| 解构 / 展开 | ✗ |
| `Array.includes()` / `map` / `filter` / `some` | ✗ |

→ **除 `endsWith` 外零 ES6+ 依赖**，兼容性缺口实际为零。

`README.md` 的「PAC 文件的结构与判定口径」小节新增一段
**「关于删除的 `endsWith` polyfill」**，记录：删除判断依据四条、
与 Firefox 无关的澄清、沙箱风险、以及「正确解法是不依赖 `endsWith`
而非加回 polyfill」这一结论。

### ★ 方法论收获（可复用）
> **面对「兼容性 polyfill」这类代码，先查清它到底在防什么，再决定去留。**
> 判断链：① 这个 API 什么时候进入基线 → ② 目标运行时是否早已支持 →
> ③ polyfill 本身在目标环境是否可能失败（沙箱/只读原型）→
> ④ 若真需兼容，是「加 polyfill」还是「改用低版本 API」更对。
> 本例答案是④「改用低版本 API」，且④其实也不需要。

`.fhead` 是 flex 容器，我往里放了四项（标题 / 路径 / 计数 / 搜索框）却没设收缩规则，
flex 默认允许压到内容下限 → 中文标题被挤成逐字换行。
**修法**：标题与计数加 `flex:0 0 auto` + `white-space:nowrap`（不许压缩），
空间不足时由 `.fpath`（路径，可有可无）承担压缩。

### ★★ 根因二（更隐蔽）：全局 `input[type=text]{width:100%}` 覆盖了搜索框
复测时发现搜索框实测宽 **916px**（= 容器全宽），而 `.pacsearch` 明明写了 `width:200px`。
用 CDP 查计算样式才找到真凶：**第 114 行有一条通用的
`input[type=text],input[type=number],textarea{width:100%}`**（给参数设置表单用的），
它与 `.pacsearch` 同为 0-1-0 特异性且**写在后面** → 后写的胜，搜索框被拉满整行；
又因 `flex:0 0 auto` 不许收缩，**把 `.fpath` 挤成 0 宽**（路径完全不可见）。
**修法**：把 `.pacsearch` 的定义移到第 114 行**之后**，并提升特异性为
`.fhead .pacsearch`（0-2-0）。双保险。

★ 教训：**同特异性下 CSS 后者胜**。给特定元素加样式前，先想想有没有通用选择器
（`input[type=...]`、`a`、`p` 之类）在后面覆盖它。**改完必须查 computed style 复核，
不能只看源码里写了什么。**

### 改动（`html/console.html`）
1. `.fhead b` → 加 `flex:0 0 auto;white-space:nowrap`
2. `.pachit` → 加 `flex:0 0 auto;white-space:nowrap`
3. `.fpath` → `flex:1 1 0;min-width:0`（吸收剩余空间、可缩到 0 并省略号）
4. `.pacsearch` / `:focus` → 移到通用 input 规则之后，选择器升级为 `.fhead .pacsearch`
5. `PAC_RENDER_LIMIT`：1000 → **200**（主人指示）

## 追加：访问日志界面限制为最多 200 行（15:42）

### 需求
主人：「访问日志界面上最多显示200行，不要全部显示」

### 关键判断：上限放后端而不是前端
原实现：`service.go` 的 `handleAccessLog` 里 `const maxLines = 400`，
前端 `loadLog()` 拿到多少渲染多少。
→ **改后端**：少读少传（400 行 JSON → 200 行），前端逻辑不用动，
`truncated` 标记与计数自然对上。前端本来就是「照单渲染」。

### 关于搜索范围的取舍（已与主人确认）
后端只给 200 行，而前端的过滤是在**已拿到的数据**上做的
（`rows.filter(...)`）→ 意味着**搜索也只能在这 200 行内**。
当时日志文件有 1616 行，更早的记录搜不到。
给主人列了三个选项（①就限 200 行、搜索也在 200 内 ②只限渲染、搜索扫更大范围
③加「加载更多」按钮），**主人选①**，最简方案。

### 改动
1. **`service.go`**：`maxLines` 400 → 200，并把两个上限提为包级常量
   （`logTailMaxBytes = 512*1024`、`logMaxLines = 200`），便于测试引用与集中修改。
   注释写明「上限放后端而非前端」的理由，以及「搜索也只在这批数据内」。
2. **`html/console.html`**：改统计文案。原来有截断时显示
   `200/200 条 · proxy N · direct N · 已截尾` —— **`200/200` 容易被误读成
   「日志总共就 200 条」**。改为：
   - 有截断 + 未搜索 → `最近 200 条 · proxy N · direct N · 更早记录未显示`
   - 有截断 + 搜索中 → `3/200 条 · proxy N · direct N · 更早记录未显示`
